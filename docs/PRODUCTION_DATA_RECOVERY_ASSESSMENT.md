# Production data recovery assessment

Assessment date: 20 November 2026. Times marked UTC are UTC; PostgreSQL timestamps below are stored without time zone.

This is a point-in-time assessment of the then-deployed containers and recovered snapshots. Subsequent local reliability commits added durable preprocessing and prediction checkpoints; the current preprocessing source uses `earliest` for a missing offset, while current prediction uses `latest`. Those source changes were not a production deployment and do not recover the historical Kafka data or offsets described here. Recheck the actual deployed images and configuration before any separately authorized recovery.

## Decision: PARTIAL HISTORICAL RECOVERY POSSIBLE

An independently readable InfluxDB backup and PostgreSQL dump from 11 November were restored into isolated services. They provide partial historical database snapshots. All 20,631 telemetry points in the InfluxDB backup already exist in production with identical stored fields and values, so this backup has not been shown to recover any missing production telemetry. Recovery of the expired Kafka offsets, historical Kafka telemetry, preprocessing stream, and prediction-topic records is **not established**. Retained InfluxDB predictions remain available, but are not a backup of the original Kafka records.

The discovery covered the project repository, the identified `D:\PMS-backups` directory, and Docker volumes and environments visible on this host. It does not establish that no other external or offline backup exists. Production consumers were not restarted, and no production recovery was executed.

## Isolated restoration and comparison

New InfluxDB 2.7 and PostgreSQL 16 containers were started under a separate Compose project, with a project-specific network, no published host ports, new data volumes, and the backup directory mounted read-only. No production volume was mounted for writing. The InfluxDB backup was restored to a separately named organization and bucket; the PostgreSQL dump was restored to the isolated database. Both operations succeeded.

The temporary isolated containers and their network were subsequently removed; their volumes were retained. The InfluxDB data and configuration volume IDs are `aa07d32fd5d81894fc42c73311900502d22ae4ad965220265e95477d22eb9434` and `19c43a8d5559a72d68649e60158b76a3ee5069423fd9b20652583152ef9e7c80`; the PostgreSQL data volume ID is `4910515f32f49d66e9dfe735814b92316488ced06e2d5d0f80b792166a9089b4`.

The restored InfluxDB run is FD001, run `5641844e03004a7fb4d36438003fc731`, from 2026-11-11 14:33:42.544708744 UTC to approximately 14:38:48.901833 UTC. Comparing measurement, tags, timestamp, field name and numerical value against production showed:

* 20,631 restored point identities are present in production; zero restored point identities are missing there.
* All 515,775 restored field values match production: 25 fields per point, including 21 sensor values, three operational settings and `time_cycles`. Zero compared fields were missing or different; no duplicate restored field identities were found.
* Production contains another 20,671 point identities outside that backup run. Their absence from the backup is consistent with its earlier snapshot and is not evidence they have been lost from production.

This establishes equality of the stored snapshot for the compared run, not equality of original Kafka payloads or a complete history. InfluxDB point identity is determined by measurement, tag set and timestamp; a later write with the same identity can merge or replace field values. Consequently, a current snapshot cannot reveal all past duplicate writes or downstream effects. Event IDs are not among the stored telemetry fields or tags inspected.

The PostgreSQL restore contains `users` (1 row), `audit_logs` (2), and zero rows in each of `email_verification_tokens`, `password_reset_tokens`, and `revoked_tokens`. Production had respectively 3, 48, 6, 0 and 3 rows, and also had `alerts` (14), `alert_audit` (24), and `anomaly_records` (20), which are absent from this dump. Hashed row-ID comparison found the restored user and two audit IDs in production; it does not establish equality of all row values. The restored user creation timestamp is 2026-11-11 14:36:49.689225, and the restored audit timestamps range from 2026-11-11 14:34:28.421987 to 14:36:49.702768, without time zone. Credentials and token contents were not included in this report.

### Identifier reconciliation and prediction coverage

The comparison preserves each original string. As a separate comparison key, accept only nonnegative decimal digits optionally followed by a decimal point and one or more zeroes, and convert the integer part to a canonical integer string; reject any other representation for manual review. Keep the original alongside the canonical key, because normalization itself is many-to-one and cannot reconstruct the original spelling. Match using dataset, run, canonical unit, cycle and timestamp, and check for multiple candidates before accepting a match. This is an analysis rule, not authorization to change stored data.

The prior read-only export contained 100 distinct telemetry unit strings, all integer-form; predictions contained 101 distinct strings: 100 decimal-zero forms and integer `1`. All 59,044 inspected telemetry and prediction rows matched the accepted syntax. Within each dataset and run there were zero canonical unit keys with multiple original spellings on either side. Before normalization, 11 prediction rows matched and 17,731 did not; afterward 17,742 matched and zero did not. There were zero duplicate comparison keys on either side and zero prediction rows with multiple candidate telemetry rows under the complete comparison key. The same canonical unit can occur in different runs, which remain separate keys; this result is limited to the inspected snapshot.

As a coverage diagnostic, assuming contiguous cycles beginning at 1 and one prediction per cycle starting at cycle 30, the later full run has all 17,731 eligible cycles represented, and the 40-cycle acceptance run has all 11 represented. The earlier backed-up run has 17,731 such eligible telemetry cycles and **zero** observed predictions. Whether predictions were intended or enabled for that run is unknown; do not label the difference a confirmed loss. A prediction-to-telemetry match is not proof of model correctness or complete downstream processing.

## Kafka and historical recovery limitations

The preceding production investigation recorded expiration of the three groups on 19 November 2026 at approximately 12:39 UTC. Their last documented committed offsets were 20,671 for `influxdb-writer-group` and `preprocessing-service-group` on `sensor-telemetry`, and 20,671 for `rul-prediction-service-group` on `preprocessed-telemetry`. Those offsets are no longer available through the normal group API. At that investigation, earliest and latest offsets were both 20,671 for each of those two topics and both 17,742 for `rul-predictions`; the application topics therefore retained no historical records. These offsets are historical observations, not a substitute for rechecking immediately before any eventual recovery.

The backup of one InfluxDB run cannot recreate original MQTT or Kafka envelopes, event IDs, topic offsets, preprocessing outputs, prediction windows or side effects. Existing RUL points are useful historical outputs, but the original prediction-topic messages are not established as recoverable. The full later production telemetry run is available in InfluxDB but was not in the validated earlier backup. Source C-MAPSS files can create a new run, not reproduce the original event history exactly.

## Recovery recommendations — do not execute yet

For all three groups, retain the current stopped state while obtaining an up-to-date, independently verified backup of production databases and investigating the unvalidated old volumes and any external exports. Record current topic bounds, group state, data provenance and application image versions immediately before a separately approved deployment. Test the intended consumer images and a representative data copy in an isolated environment; reconcile point identities and values, processing state, prediction outputs and side effects. Choose explicit starting offsets only after deciding how to handle the gap, with a rollback and monitoring plan. Never restore an older database snapshot over production as a substitute for reconciliation.

* **`influxdb-writer-group`:** the deployed ingestion container uses older source than the frozen Module 02 checkout and uses `earliest` on a missing offset. Confirm the intended image and its compatibility before deployment. With an empty retained topic, `earliest` cannot recover old records; if new records accumulate before startup it can read them from the then-current earliest position. Reconcile existing InfluxDB identities and values before any replay. Identical point identities do not make all processing and side effects automatically safe.
* **`preprocessing-service-group`:** the inspected deployed consumer uses `latest` when no offset exists. Starting after producers could skip already-arrived records. Account for its in-memory preprocessing state, choose and verify an intentional start position and warm-up procedure, and compare regenerated results against any independently recovered originals. No original preprocessing stream backup was validated.
* **`rul-prediction-service-group`:** the inspected deployed consumer also uses `latest` for missing offsets. Its prediction window needs 30 cycles and is in memory, so controlled warm-up and per-unit ordering matter. Reconcile outputs and alert or other downstream effects before allowing writes; avoid interpreting a regenerated prediction as proof of the original output.

Plan producer and consumer startup order together: establish the consumer configuration, selected offsets, state and readiness before admitting new production events. Validate behavior with the exact deployable images. The old deployed ingestion source and the newer frozen Module 02 source must not be assumed equivalent. These recommendations do not authorize a restart, offset reset, database modification or deployment.

### Proposed validation, cutover and rollback gates

1. Obtain a current verified backup and capture a read-only baseline of topic partition bounds, group metadata, images, configuration, InfluxDB identities/values, PostgreSQL state and downstream outputs. Identify an operator, maintenance window, durable event source and monitoring thresholds. Decide explicitly how future events are held while consumers are unavailable; broker retention still applies.
2. In isolation, deploy the exact candidate versions, replay a representative copy with unique test identities, exercise missing/out-of-range offsets, delayed consumers, duplicates and restart. Reconcile raw-to-Inﬂux point identities and field values, per-unit preprocessing state, prediction cycles after 30 contiguous samples and all alert or other side effects. Test the observed unit-string mismatch without modifying production identifiers. Measure throughput and lag against expected arrivals.
3. Before a separately authorized cutover, freeze producer admission or provide a durable buffer, recheck current topic bounds, and document an explicit per-partition starting position for each group. Verify each consumer's actual reset and commit behavior and prevent silent fallback. Establish preprocessing and prediction readiness and the warm-up approach before allowing source traffic; start producer traffic only when all required paths are ready. If buffering is impossible, define and accept a specific gap before proceeding.
4. Monitor lag, errors, data counts, identity/value reconciliation, skipped cycles, prediction warm-up and side effects. Stop admitting new events and halt the affected recovery if a threshold or reconciliation gate fails. Preserve logs, offsets and outputs for diagnosis. A rollback should return to a previously validated image/configuration under a separate approved procedure, with a new explicit per-partition position and reconciliation; merely redeploying the old image does not undo writes, restore lost data or reverse notifications. Never overwrite production with the older snapshot as an automatic rollback.

## Remaining unknowns and next steps

1. Seek external, offline and other-host Kafka exports, database backups, and archived simulator output; inspect the identified old restore/test volumes further with read-only mounts. Establish provenance and timestamp coverage before classifying them as backups.
2. Determine the expected production collection schedule and run inventory, so unobserved time intervals can be distinguished from intentional idle periods.
3. Establish whether event IDs, preprocessing vectors, historical group offsets or original prediction messages exist in another source. The checked backups do not establish this.
4. Reconcile the unit tag representation mismatch and inspect any downstream alert or prediction side effects in an isolated copy.
5. Prepare a separately reviewed deployment and recovery runbook with explicit starting offsets, image versions, warm-up, sequencing, monitoring and rollback. Do not restart production consumers until those decisions are made.

The assessment uses read-only production queries and isolated restores. It does not establish that restarting any production consumer is safe.
