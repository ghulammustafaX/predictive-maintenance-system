# InfluxDB telemetry schema (Module 03)

This describes the **currently implemented** raw Kafka-to-InfluxDB writer in `ingestion/src/kafka_consumer.py`, rather than a proposed migration. InfluxDB is version 2.7 in `docker-compose.yml`.

## Raw measurement: `sensor_telemetry`

The destination org and bucket are configured by `INFLUXDB_ORG` and `INFLUXDB_BUCKET`, rather than hard-coded. The main Compose stack initializes an initial bucket with `DOCKER_INFLUXDB_INIT_BUCKET`; existing bucket settings are not modified by this document.

| Kind | Name | Stored type / behavior |
| --- | --- | --- |
| Measurement | `sensor_telemetry` | Raw telemetry |
| Tag | `dataset_id` | String, normally `FD001` to `FD004`; legacy messages without this field use `unknown` |
| Tag | `unit_id` | Normalized decimal string of the engine number, such as `5` |
| Tag | `run_id` | String run identity; legacy messages without this field use `default` |
| Tag | `cycle` | Decimal string from `time_cycles`, indexed as a tag in the **existing** schema |
| Field | `time_cycles` | Integer |
| Fields | `operational_setting_1`, `operational_setting_2`, `operational_setting_3` | Floats, required |
| Fields | `sensor_1` to `sensor_21` | Floats when present; missing/none values are omitted |
| Timestamp | `_time` | Explicit message `source_timestamp` if provided and nonempty, else `timestamp`; neither is generated by InfluxDB |

The writer validates payloads and supplies a source-derived timestamp. A missing timestamp is rejected. A repeated write with the same **measurement, complete tag set and timestamp** addresses the same InfluxDB point, which may merge/overwrite fields; this does **not** create exactly-once processing across Kafka and InfluxDB. The Kafka consumer uses synchronous single-point writes, then commits each offset only after a successful write (or confirmed dead-letter publication). It is an **at-least-once** pipeline.

**Indexing caveat:** `cycle` is currently a tag. This preserves the accepted writer contract but raises a cardinality concern for long or high-volume runs. Any schema change would require a separately reviewed migration and compatibility tests; do not silently remove the tag.

## Query examples (InfluxDB Flux)

Replace `sensor-data` with the configured bucket name. These examples assume stored timestamps fall within the specified time range.

### Latest ten cycle readings for one engine in one dataset and run

```flux
from(bucket: "sensor-data")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "sensor_telemetry")
  |> filter(fn: (r) => r._field == "time_cycles")
  |> filter(fn: (r) => r.dataset_id == "FD001" and r.unit_id == "5" and r.run_id == "YOUR_RUN_ID")
  |> group(columns: [])
  |> sort(columns: ["_time"], desc: true)
  |> limit(n: 10)
```

### Average sensor 1 by dataset and engine in the selected time range

```flux
from(bucket: "sensor-data")
  |> range(start: -24h)
  |> filter(fn: (r) => r._measurement == "sensor_telemetry" and r._field == "sensor_1")
  |> group(columns: ["dataset_id", "unit_id"])
  |> mean()
```

### Bounded, query-time reduction for one run

```flux
from(bucket: "sensor-data")
  |> range(start: -1h)
  |> filter(fn: (r) => r._measurement == "sensor_telemetry" and r.dataset_id == "FD001")
  |> filter(fn: (r) => r.unit_id == "5" and r.run_id == "YOUR_RUN_ID" and r._field == "sensor_1")
  |> aggregateWindow(every: 1m, fn: last, createEmpty: false)
```

Query-time `aggregateWindow` does **not** constitute scheduled or persisted downsampling. The backend fleet and telemetry APIs also perform their own bounded Flux queries.

## Retention and provisioning

The production Compose configuration initializes the configured bucket on first setup, but does **not** automatically apply a 90-day retention period. **Existing production buckets and retention rules are not changed by this module.**

`bucket_policy.py` and `setup.sh` are **standalone, operator-invoked tools**. They do not run as Docker initialization hooks or modify the main Compose stack.

- With only `--bucket NAME --retention-seconds N`, the tool reads the existing organization and bucket, verifies the retention matches, and exits without mutation. A missing bucket or mismatch fails closed.
- A missing bucket may be created only if both `--create-if-missing` and the exact-name environment confirmation `PMS_BUCKET_CREATE_CONFIRM=NAME` are supplied. Existing buckets are **never updated or deleted** even when this option is enabled.
- `N=0` means infinite retention. Finite retention must be at least 3,600 seconds (one hour); an upper validation bound of ten 365-day years applies. No implicit 90-day default is applied.
- For a newly provisioned 90-day bucket, `N=7776000`. Expiration can delete points based on their recorded timestamps. Do **not** apply this to an active existing bucket without explicit retention, archival, migration and rollback approval.

Illustrative standalone commands after installing `storage/influx_init/requirements.txt` and configuring `INFLUXDB_URL`, `INFLUXDB_TOKEN` and `INFLUXDB_ORG` to point to an authorized, isolated instance:

```sh
# Read-only inspection; must match existing retention to succeed.
python storage/influx_init/bucket_policy.py --bucket m3-isolated-bucket --retention-seconds 0

# Explicit, new bucket creation only. No existing bucket is ever patched.
PMS_BUCKET_CREATE_CONFIRM=m3-new-test python storage/influx_init/bucket_policy.py \\
  --bucket m3-new-test --retention-seconds 7776000 --create-if-missing
```

These commands are examples, not approval for execution on production. The isolated CI probe creates throwaway, uniquely named buckets and verifies no-mutation behavior on the existing isolated telemetry bucket.

## Isolated verification

The Module 03 verification environment is defined in `docker-compose.module3-verification.yml` and uses its own Docker project, network, Kafka topic/group, org and InfluxDB instance. Its probe exercises the **real existing ingestion consumer** and queries an isolated InfluxDB, without production credentials or volumes.
